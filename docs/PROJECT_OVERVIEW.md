# Ознакомительный документ по проекту ISP Telegram Bot

> Этот документ предназначен для быстрого погружения новых разработчиков в архитектуру, основные модули и правила работы над проектом. Он агрегирует информацию из существующих README и технических файлов и описывает взаимосвязи между компонентами системы.

## 1. Общий обзор

- **Назначение проекта** – Telegram‑бот, который помогает монтажникам фиксировать новые подключения, вести учет материалов/оборудования и формировать отчёты.
- **Стек** – Python 3.11, библиотека `python-telegram-bot v21`, `sqlite3`, `openpyxl`, `Pillow`.
- **Основные сценарии**: создание отчёта о новом подключении, выпуск сводных отчётов, управление сотрудниками и их остатками материалов.

## 2. Архитектура высокой степени

Проект выстроен по многослойной схеме:

| Слой | Содержимое | Ответственность |
| --- | --- | --- |
| Presentation | `bot.py`, папка `handlers/` | Обработка команд и callback, сценарии диалогов, валидация пользовательского ввода |
| Business Logic | `handlers/**`, `utils/`, `report_generator.py` | Реализация сценариев (создание подключений, отчёты, управление сотрудниками), формирование текстов/клавиатур |
| Data Access | `database/` | Работа с SQLite: репозитории по сущностям, логирование движений, миграции |
| Data Storage | `isp_bot.db` | Физическое хранение данных и логов движений |

Коммуникация идёт сверху вниз: handlers используют `Database` и утилиты, а отчётность (Excel) строится через `report_generator` и `handlers/reports`.

## 3. Основные модули и взаимосвязи

### 3.1 `bot.py`

- Точка входа. Подключает конфигурацию (`config.py`), создаёт `Application`, регистрирует ConversationHandler из модулей `handlers.connection`, `handlers.employees`, `handlers.reports`.
- Настраивает глобальные логгеры и запускает `run_polling()`.

### 3.2 `config.py`

- Хранит идентификаторы состояний ConversationHandler (например, `SELECT_CONNECTION_TYPE`, `ENTER_FIBER` и т.д.).
- Загружает переменные из `.env` (токен бота, ID администраторов, канал для отчётов).
- Определяет глобальные константы (тип подключения, сообщения об активации).

### 3.3 Модуль подключений (`handlers/connection/`)

| Файл | Назначение |
| --- | --- |
| `conversation.py` | Определяет ConversationHandler с последовательностью шагов (17 стадий) для создания отчёта. |
| `steps.py` | Реализует обработчики конкретных шагов: выбор типа подключения, загрузка фото, ввод адреса, выбор оборудования (включая SFP модуль), подтверждение договора, телеграм‑бот. |
| `cabling.py` | Управление шагами 7–9 (порт, ВОЛС, витая пара). Содержит логику обработки «Пропустить». |
| `devices.py` | Интерактивные шаги для оборудования (роутеры, SNR‑боксы, ONU, медиаконверторы, SFP). |
| `validation.py` | Проверяет остатки материалов/оборудования у исполнителей, управляет выбором плательщиков. |
| `confirmation.py` | Формирует итоговое подтверждение, списывает материалы/оборудование через `Database`. |
| `comments.py`, `executors.py`, `ui.py`, `constants.py` | Вспомогательные шаги/инструменты (комментарий, выбор исполнителей, фабрики клавиатур, текстовые шаблоны). |

**Связи:** `conversation.py` импортирует обработчики из всех вложенных модулей, оборачивая их в `ConversationHandler`. Каждый шаг обращается к `db` через `run_in_thread`, чтобы не блокировать event‑loop.

### 3.4 Модуль управления сотрудниками (`handlers/employees/`)

- Содержит подмодули `flow.py`, `materials.py`, `routers.py`, `onu.py`, `media_converters.py`, `sfp_modules.py`, `start.py` и др.
- `EmployeeFlow` – фасад, который объединяет логику сотрудников и ресурсов. В `start.manage_resources_start` собирает меню «Материалы и оборудование» (материалы, роутеры, ONU, медиаконверторы, SFP).
- Раздел ресурсов работает в двух режимах: управление балансами и выдача оборудования при подтверждении подключения.

### 3.5 Репозитории (`database/`)

- `db_manager.py` – центральный объект `Database`. Инициализирует репозитории, применяет миграции (v1–v7), предоставляет фасадные методы (добавить сотрудника, списать материалы, логировать движения).
- `repositories/*.py` – реализация паттерна Repository для таблиц: `employee`, `material`, `router`, `snr_box`, `onu`, `media_converter`, `sfp_module`, `connection` и др.
- Все списания материалов/оборудования одновременно фиксируются в таблице `material_movement_log`, что нужно для листа «Движение материалов» отчётов Excel.

### 3.6 Утилиты (`utils/`)

- `helpers.py` – вспомогательные функции: отправка отчётов, формирование текста подтверждения, запуск блокирующих вызовов БД в потоке (`run_in_thread`).
- `keyboards.py` – фабрики reply/inline клавиатур, используемых в нескольких модулях.
- Дополнительные файлы (validators, formatters) используются для валидации и форматирования сообщений (часть логики перемещена в handlers).

### 3.7 Генератор отчётов (`report_generator.py`)

- Использует `openpyxl` для создания Excel файлов: индивидуальные отчёты по монтажнику, глобальные отчёты и лист «Движение материалов».
- Работает совместно с `handlers/reports`, который собирает параметры (сотрудник, период) и инициирует генерацию.

## 4. Взаимодействие модулей при создании подключения

1. Пользователь нажимает «📝 Новое подключение» (`handlers/connection/conversation`).
2. `steps.new_connection_start` запускает state machine: выбор типа → загрузка фото → адрес.
3. Далее подключается `devices.py` (роутеры, SNR, ONU, медиаконверторы, SFP). Все выбранные значения и количества сохраняются в `context.user_data['connection_data']`.
4. Шаги 7–9 (`cabling.py`) собирают порт и метраж (есть возможность «Пропустить»).
5. После выбора исполнителей (`executors.py`) запускается `validation.py`, который проверяет, у кого достаточно материалов/оборудования. Итоговый плательщик сохраняется в `context.user_data`.
6. `confirmation.py` показывает пользователю итоговую сводку и по подтверждению вызывает `db.create_connection`, где в одной транзакции записывается подключение, связи с сотрудниками, фотографии и логируется списание материалов/оборудования (включая модели SFP).
7. `send_connection_report` формирует текст отчёта + отправляет фото и, при необходимости, публикует их в канал.

## 5. База данных и миграции

- **Основные таблицы:** `employees`, `connections`, `connection_employees`, `connection_photos`, `material_movement_log`, `employee_routers`, `employee_snr_boxes`, `employee_onu`, `employee_media_converters`, `employee_sfp_modules`.
- **Миграции:** реализованы вручную в `db_manager.py` (методы `_migration_v1 … _migration_v7`). При инициализации `Database` проверяет таблицу `schema_migrations` и применяет недостающие шаги.
- **Лог движений:** все операции (материалы, роутеры, медиаконверторы, ONU, SNR, SFP) фиксируются с типом `add`/`deduct` и привязкой к `connection_id`, что позволяет строить лист «Движение материалов».

## 6. Правила и договорённости разработки

1. **Асинхронность:** все handlers – `async`; любые тяжёлые операции (БД, генерация отчётов) запускаются через `run_in_thread`, чтобы не блокировать event loop.
2. **Состояния ConversationHandler:** реальные шаги перечислены в `config.py`. Новые состояния нужно добавлять туда же и регистрировать в соответствующем ConversationHandler.
3. **Валидация и отмена:** каждое текстовое состояние обязано проверять `CANCEL_TEXT` и наличие `SKIP_TEXT`, если ожидается возможность пропуска.
4. **Логирование:** используем глобальный `logger` из `config.py`. При ошибках БД и сервисов обязательно писать `logger.exception`.
5. **Модули:** предпочтение отдаётся разделению по предметным областям (connection, employees, reports). В `utils/` оставляем только переиспользуемые утилиты.
6. **БД:** любые изменения схемы – через новые миграции в `Database._migration_v*`; при добавлении сущностей обязательно создать репозиторий либо метод в существующем репозитории.
7. **Отчёты:** при добавлении нового оборудования следует обновить `report_generator.py` (оба листа) и `database/repositories/connection_repository.py`, чтобы данные попадали в Excel.
8. **Документация:** обновлять `docs/ARCHITECTURE.md`, `docs/MODULE_GUIDE.md` и этот обзор при появлении новых модулей/правил.

## 8. Чек-лист для нового разработчика

1. Установить зависимости и поднять окружение (см. README).
2. Прочитать `docs/ARCHITECTURE.md` и настоящий обзор.
3. Изучить ConversationHandler в `handlers/connection/conversation.py`, чтобы понимать flow.
4. Посмотреть `database/db_manager.py` – понять схему миграций и сущности.
5. Ознакомиться с `report_generator.py` (нужно для любых изменений отчётности).
6. Настроить `.env`, чтобы тестировать бота локально (понадобится Telegram токен и ID админов).
7. Перед коммитом убедиться, что lint и базовые сценарии (создание подключения, управление ресурсами) работают.
